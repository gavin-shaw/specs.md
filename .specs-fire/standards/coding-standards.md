# Coding Standards

## Overview

Follow the existing specs.md style. The repository is mostly markdown, JavaScript, and TypeScript, so keep changes small, explicit, and easy to review.

## Code Formatting

**Tool**: No single formatter is enforced across the repository.
**Enforcement**: Match nearby code and run available validation.

### Key Settings

- JavaScript and TypeScript use 4-space indentation where that is the local style.
- Markdown and YAML use 2-space indentation for nested lists and mappings.
- Prefer ASCII in new files unless an existing file or user-facing requirement needs Unicode.
- Keep markdown headings and command examples stable because they are consumed by agents and documentation.

## Linting

**Tools**: markdownlint for flow markdown, ESLint for the VS Code extension, TypeScript compiler checks where configured.

### Key Rules

- Preserve generated command, agent, and skill schemas.
- Do not add dependencies without strong justification.
- Validate system boundaries: CLI inputs, installer flags, filesystem paths, package manifests, and external command output.
- Avoid broad rewrites when a narrow fix handles the current problem.

## Naming Conventions

| Element | Convention | Example |
|---------|------------|---------|
| JavaScript variables and functions | camelCase | `installFlow` |
| Classes | PascalCase | `InstallerFactory` |
| Constants | UPPER_SNAKE_CASE | `DEFAULT_TOOLS` |
| Markdown files | kebab-case | `quick-start.md` |
| Agent files | kebab-case with role | `fire-builder.md` |
| Skill directories | kebab-case | `project-init` |

## File Organization

```text
src/
  bin/                 CLI entry points
  lib/                 Installer and dashboard library code
  flows/               Flow definitions, agents, commands, skills, templates
  __tests__/           Vitest tests and schema validation
docs.specs.md/         Documentation site content
vs-code-extension/     VS Code extension source
memory-bank/           Existing project memory artifacts
.specs-fire/           FIRE state, intents, runs, and standards
```

## Imports

- Prefer built-in Node modules first, then external packages, then local modules.
- Keep CommonJS modules in existing CommonJS files.
- Keep TypeScript imports idiomatic in extension and test code.

## Error Handling

- CLI errors should be user-friendly and actionable.
- Exit with meaningful process codes when commands fail.
- Do not expose stack traces in normal user-facing command output.
- File operations should check existence and create directories recursively when needed.
- Installer changes should be reversible by inspecting the generated diff.

## Logging

- Use CLI output helpers and terminal styling already present in the codebase.
- Remove debug logging before handoff.
- Never log secrets, tokens, environment values, or private paths unless required for local troubleshooting and safe to show.

## Comments and Documentation

- Comment complex behavior and schema-sensitive code.
- Avoid comments that restate obvious code.
- Update docs when command behavior, flow structure, or install output changes.

## Preferred Patterns

### Installer Classes

Add tool-specific installer behavior through the existing installer class pattern rather than one-off procedural code.

### File-Based Contracts

Agent and skill behavior is defined by markdown, YAML, and templates. Keep those contracts readable and deterministic.

### Targeted Tests

Add or update tests near the changed behavior. Prefer schema and installer tests for flow packaging changes.

## Anti-Patterns

- Hidden git writes by agents or scripts.
- Hand-editing generated runtime files when source templates should change instead.
- Mixing unrelated refactors into feature or bug-fix changes.
- Adding framework dependencies for simple filesystem or CLI behavior.
