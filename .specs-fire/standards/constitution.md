# Project Constitution

Universal policies that apply to all code in this project. Module standards may add detail, but they do not override this constitution.

## Git Workflow

- The user is the only entity that commits, pushes, opens pull requests, amends, force-pushes, or performs other git-write operations unless the latest user message explicitly asks for that exact action.
- Implementation work stops at an uncommitted diff. Staged changes are acceptable when requested, committed changes are not.
- Use Conventional Commits when the user later commits changes, for example `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, or `test:`.
- Keep `main` deployable and merge feature branches through review.

## Code Review

- Review for behavior, maintainability, tests, and documentation impact.
- Security-sensitive changes require extra scrutiny.
- Do not self-merge or bypass review gates.

## CI/CD

- Pull requests should pass tests and relevant validation before merge.
- Prefer targeted checks while developing, then run broader validation before handoff.
- Keep generated runtime files out of source control unless the project explicitly documents them as source.

## Security

- Never store secrets, credentials, API keys, tokens, or private environment values in code or committed configuration.
- Treat installer inputs, filesystem paths, and external command responses as system boundaries.
- Use trusted dependencies and avoid new packages unless the benefit is clear.

## Documentation

- Keep README, docs, and generated flow guidance aligned with behavior.
- Breaking changes need migration notes or changelog coverage.
- Public commands, installer options, and flow artifacts should be documented.
