# Testing Standards

## Overview

Use the repository's existing test commands and validation layers. Scale test coverage to risk: installer, schema, and flow packaging changes usually need automated checks; documentation-only updates may only need markdown validation.

## Testing Framework

**CLI package**: Vitest
**VS Code extension**: Mocha with VS Code test runner
**Markdown validation**: markdownlint

## Test Types

| Type | Tool | Location | When to Use |
|------|------|----------|-------------|
| Unit tests | Vitest | `src/__tests__/unit/` | Installer, schema, parser, and utility behavior |
| Schema validation | Vitest plus YAML schemas | `src/__tests__/schemas/` | Agent, catalog, memory-bank, context, and skill contracts |
| Markdown lint | markdownlint | `src/flows/**/*.md` | Flow command, agent, skill, and documentation markdown |
| Extension tests | Mocha and VS Code test runner | `vs-code-extension/src` and compiled tests | Extension command and UI behavior |

## Coverage Expectations

- Add targeted tests for behavior changes in installers, parsers, validators, and dashboard logic.
- Update schema fixtures when markdown/YAML contracts change.
- For generated flow artifacts, test the source templates or installer behavior rather than only the generated output.
- Include regression tests for bug fixes when practical.

## Test Naming

Use descriptive test names that state the expected behavior.

Examples:

- `patch-root-gitignore.test.ts` verifies installer `.gitignore` patching behavior.
- `bundle-script-deps.test.ts` verifies dependency bundling behavior.
- `markdown-schema.test.ts` verifies markdown contract validity.

## Test Structure

```ts
import { describe, expect, it } from "vitest";

describe("feature area", () => {
    it("does the expected thing", () => {
        // arrange
        // act
        // assert
    });
});
```

## Mock Strategy

- Mock filesystem and process boundaries when testing installer logic.
- Prefer temporary directories for integration-style filesystem tests.
- Keep mocks small and focused on the boundary being exercised.

## Test Data

- Store reusable fixtures near the tests that consume them.
- Keep generated artifacts deterministic.
- Avoid absolute machine-specific paths in snapshots or fixtures.

## Running Tests

```bash
# Run all root validation
npm run validate:all

# Run CLI package tests
cd src && npm run test

# Run markdown lint
cd src && npm run lint:md

# Run VS Code extension tests
cd vs-code-extension && npm run test
```
